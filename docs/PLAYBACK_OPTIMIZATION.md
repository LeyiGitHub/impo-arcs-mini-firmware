# 播放阶段优化

在 `codex/voice-latency` 的 `1d9c33b` 上继续实施。沿用官方 `/tts`、原音色、WAV、
Link/Noise/TLS 和“小周小周”。上传仍为 batch / 1200 ms；本轮只比较播放策略。
最终设备采用adaptive/1200/full。最终镜像20轮交错对照的自动声学首声P50
从7.959秒降至4.756秒，点估计缩短40.2%；另8轮短文本回归也完成，28轮无
欠载或接收溢出。声学有效数、实验条件和未验收边界见下文。

## 实现

- 64 KiB PSRAM 音频接收环，回调仅作有界复制和状态发布。独立4 KiB栈解码任务
  处理WAV和重采样，等待PCM空间不会堵住Link接收任务。音频输出优先于解码，
  解码优先于网络；每块让出调度。接收环溢出明确失败，不丢字节后伪装完整。
- 复用原30秒PCM环。完整缓存模式保留原完整/25秒起播策略；adaptive初值可配置，最终产品1200 ms，
  短音频完整后即使不足阈值也释放。欠载时补静音并再缓冲，按原位置续播，阈值
  每次增加200 ms，最大2000 ms。符合条件的后续播报继承阈值，连续干净播放后
  逐步降低。该策略不是对未来网络带宽的保证。
- 可选分句TTS只切分已确认的完整最终文字。按中文句末、问号、感叹号和换行
  合并段落，不以小数点/英文缩写分句，不改变文字字节次序。首段较短，后续合并。
  当前段下载完成、原流释放且PCM空间足够后，边播放边预取下一段；最多一笔
  活跃TTS，同一播报使用一个声音代次，不清空尚未播放的前段PCM。
- sink绑定请求代次，取消后旧回调不会操作新解析器；显式say仍替换旧声音。
  speaker.stop同时取消TTS，下载/解码取消会停止整个段队列。已开始播放后的失败
  不触发原来的整篇自动重念。空WAV、声明长度不足、格式错误及溢出都明确失败。
  45秒无收包进展也明确失败；尚未出声时保留原SDK的一次TTS重试策略。
- 新增公共配置/快照和 `playback` 查询，记录收包、首PCM、首驱动写入、队列、
  欠载、分段、接收环高水位及解码栈余量。驱动接受不是DMA完成或声学首声。

## SDK配置

`impo_arcs_playback.h` 提供 `impo_arcs_mini_configure_playback()` 和
`impo_arcs_mini_playback_snapshot()`。仅在语音下载/解码和声音播放均空闲时配置。
快照 `active` 只表示下载/解码尚未完成，仍须结合声音状态判断实际播放结束。
公共头文件有新增结构字段，应用须重新编译。

```json
"playback": {"mode": "adaptive", "prefill_ms": 1200, "sentence_tts": false}
```

原产品未配置时默认 complete。独立 `products/arcs-mini2-playback.json` 使用
adaptive/1200/full，其他产品和上传默认不变。运行配置不写KV，重启恢复产品设置。

语音阶段6的`tts_request`现在表示向播放任务提交最终文字，不等于第一笔HTTP
请求已发出。以播放快照的request/first_body/first_pcm/first_write及实际声学
记录区分各阶段；first_write是驱动接受时刻。停止后保留上一播报计数，完成后
的幂等stop不会标记成取消。

```text
playback
playback complete 800 full apply
playback adaptive 800 full apply
playback adaptive 800 sentence apply
```

应用可在`on_init`中覆盖产品配置，或在声音空闲时从任务调用：

```c
impo_arcs_playback_config_t config = {
    .adaptive = true, .prefill_ms = 1200, .sentence_tts = false
};
int rc = impo_arcs_mini_configure_playback(&config); /* busy: -1 */
```

为保留的0.1.8 AP构建：

```sh
ARCS_BASE=/path/to/listenai-sdk-0.1.8 python3 tools/build.py --docker \
  --arcs-sdk-version 0.1.8 --product products/arcs-mini2-playback.json
```

该产品仍须设备原ROMFS已有匹配的小周模型。SDK源码包不含模型或已配对配置，
旧产品和最小按键示例继续走原配置；调用者不必复制Link、TTS或固件启动代码。

## 验证

主机执行实际并发解码/输出，覆盖完整缓存、提前起播、欠载再缓冲后的样本数及
PCM哈希一致、分段文字拼接、旧回调、取消、空/截断WAV、接收环溢出和短回调。
AddressSanitizer/UndefinedBehaviorSanitizer通过；常驻任务的进程结束泄漏检查关闭。
0.1.6完整主机套件、默认产品、按键示例，以及0.1.8独立候选构建通过。干净0021
补丁前缀升级到0022及重复prepare通过。静态RAM不是任务栈峰值证明。

设备候选已完成唯一Recovery、保留AP、PSRAM声明及唤醒资源核对，两份写前全片
一致、独立CP读回和全部非CP字节比较。下面对照使用候选CP `8002896a386ee81e3ea5b450607e77526ec35f9ebf23fa4b4756018a16b11939`，
1,871,192 B，ListenAI 0.1.8；同一启动、同一镜像运行时切换策略。设备20%、
Mac输出25%/输入36%，固定最终文字，10个循环中轮换三种策略顺序，共30次。
每次均使用官方`/tts`，未重试，30/30完整播放，接收环溢出0。

| 策略 | 完整 / 尝试 | 声学有效 | 首声P50 | 首声P95 | 欠载次数 | 每轮TTS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 完整缓存 | 10/10 | 10 | 7.222 s | 11.250 s | 0 | 1 |
| adaptive 800/full | 10/10 | 8 | 4.494 s | 4.915 s | 0 | 1 |
| adaptive 800/sentence | 10/10 | 10 | 4.028 s | 4.537 s | 1 | 2 |

首声为TTS命令至Mac麦克风检测到回答能量的自动代理指标，依据同代次首驱动写入
日志的主机时间限定搜索窗口，排除起播前环境声。adaptive两次声学信号未通过
门限，仍保留所有尝试，不填补或算入分位数。P50点估计比完整缓存少2.728秒、
37.8%；每种仅10次、单一文本和网络条件，不能推成所有自然对话或原始固件收益。
这不是说完至回答的整链路对比，也不是人耳听感验收。

分句只额外缩短约466 ms，却在最后一轮出现一次879 ms再缓冲；完整文字字节
和段顺序未丢失的证据来自主机PCM/文字回归，实机无逐字内容标注。随后短回答探索6次均完整播放，但800/full出现一次431 ms欠载（其余五次无欠载）；全部尝试另存，不与30次数据混合。因此最终设备候选改用
adaptive/1200/full增加储备，重新做独立对照；分句保留可配置实验项。最终full策略每轮仍只一笔TTS。分句模式有多次请求及韵律变化成本，不能承诺其句间永远无停顿。
该组接收环最高18,588 B / 65,536 B，解码栈最低余量1,288 B / 4,096 B；它们是
本组运行观察，不代表任意长文本峰值。

另有独立探索9次，全部完整播放，无欠载/溢出；它使用设备时间差的粗声学窗口，
adaptive有1次声学拒绝。该组不与30次对照合并。最初两份过长shell命令未提交TTS，
保留为无效工具运行；第二次清理恢复音量时USB重枚举、启动标识变化，复位查询
无有效记录，根因未定。随后有效探索9次及匹配30次处于同一启动中，未观察复位。

公开固定字段数据：[30次匹配对照](data/playback-20261125-matched-30.json)、
[9次独立探索](data/playback-20261125-exploration-9.json)。私有日志、音频和备份
不进入Git。

## 最终交付镜像

独立Mini2产品默认adaptive/1200/full，上传batch/1200 ms，唤醒“小周小周”。
最终CP 1,871,432 B，SHA256
`90d0638523d57355c7530e3cb9893c3e19593f49425a20dc2f6d875d0e8d876c`。
保留AP 0.1.8-231-g1060feb286ef，CP PSRAM声明0x28800000/8 MiB；两份写前全片
一致、独立CP读回和全部非CP字节比较通过。静态SRAM152,736 B / 164 KiB，
PSRAM5,313,392 B / 8 MiB。默认0.1.6产品和按键示例仍使用complete缓冲。
此镜像增加停止后的计数保留、完整解码日志，并提高该产品初始缓冲；不能将上面
800 ms候选的整组数字标成它的直接实测。头文件重复声明清理后重建，CP字节
摘要与已安装镜像一致。

最终镜像使用同一固定文字、音量和Mac声学条件，10个循环轮换complete和
adaptive/1200/full，20/20完整播放；欠载0、接收溢出0，每轮仍1笔TTS。

| 指标 | complete | adaptive/1200/full |
| --- | ---: | ---: |
| 完整 / 尝试 | 10/10 | 10/10 |
| 声学有效 | 7 | 8 |
| 命令→首声代理 P50 | 7.959 s | 4.756 s |
| 命令→首声代理 P95 | 9.385 s | 5.445 s |
| 提交→首驱动接受 P50（各10次） | 7.274 s | 4.190 s |

声学P50点估计减少3.203秒、40.2%。其余5次声学拒绝均保留，未填补；分位数
仅用通过门限的成功样本。首驱动接受指标覆盖全部20次，仍不代表实际DMA或
声学起点。单一文本、每种10次的网络实测，不能作为全链路或长期性能承诺。

独立短文本交错8/8完整播放（各4次），无欠载/溢出；声学有效complete 2/4、
adaptive 4/4。语料不同、样本更小，不与中等文字合并分位数。该启动中解码栈
最低余量1,204 B / 4,096 B，匹配对照接收环最高16,384 B。

最终镜像下载中取消、播放中取消、等待迟到数据后计数不再增加、取消后新播报、
完整结束后的幂等stop及计数保留均通过独立实机检查。上述“完整播放”依据下载、
解码、驱动计数和空闲状态；未逐字人工标注音频。

外部播放“小周小周”合成录音，在设备TTS实际播放时触发1次唤醒命中及1次打断，
随后主动结束收音并恢复监听；这是录音刺激验收，不代替真人近/远场准确率与听感。
取消与合成唤醒的固定字段证据见[最终验收](data/playback-20261125-final-acceptance.json)。

数据：[最终20轮对照](data/playback-20261125-release-matched-20.json)、

## 完整问答的独立失败记录

在最终镜像的播放与取消测试后，另发起一次固定问答。设备采集丢样0、完整上传，
收到匹配ACK及一次完整最终文字，随后TTS没有返回音频。45秒无进展后工作线程
明确失败，原语音状态机执行一次“尚未起播”的TTS重试；重试仍无音频。测试工具
在120秒等待上限停止并主动取消，原问题未重新提交，第二个计划问题未执行。
事后查询仍为同一启动，后续连接转为connecting，根因尚未确定；不能将此次失败
归因于解码器，也不能宣称整链路稳定或所有问答都提速。失败数据和后续恢复另存，
没有与成功的播放对照合并。

[问答超时记录](data/voice-latency-20261125-playback-timeout-1.json)及
[固定字段验收信息](data/playback-20261125-final-acceptance.json)保留这一结果。

受控重启后配对仍在、Wi-Fi已关联且DHCP有IP，但NTP域名DNS解析持续失败，
时钟未同步，Link停在idle；没有发送新问题。这是重启后的明确上线阻塞，不能
据此断言它就是前一轮TTS超时的根因。约236秒后设备自行完成校时并重新上线，恢复问答另用新语料检查。
本分支与源码包是可配置的SDK开发快照，不标记为稳定发行。

网络恢复后，在同一最终CP镜像的新启动中，使用另一份固定问候语料做两轮batch
完整问答，2/2成功：各1次聊天上传、1次匹配回复和1次TTS，采集丢样0。数据见
[恢复问答2轮](data/voice-latency-20261125-playback-recovery-2.json)。这两次没有
对照组，不计算全链路提速。一次工具监听日志被USB输出打断，保守门禁未播放
问题；工具改为补查规范快照后再播放，该无效工具运行单独保留，不冒充一次问答。
最终查询：设备在线、配对保留、屏幕正常、空闲唤醒监听恢复，adaptive/1200/full，
设备音量20%、Mac输出25%。连续对话后的主动结束收音不计为额外问答成功。

## 复现

使用`tools/playback_bench.py`并显式给定唯一设备核对后的runtime serial、boot、
已读回镜像ledger、固定文字、recorder路径和仓库外的新输出目录。工具默认不改
音量，不重试失败请求；使用`--cycles 10`进行轮换顺序的三模式对照。
设备shell历史会缩减实际命令缓冲，工具保守要求完整UTF-8命令小于160字节。
`tools/analyze_playback_bench.py PRIVATE_DIR --output PUBLIC_JSON`仅导出固定数字
字段、镜像和文本摘要；原始记录留在私有目录。

## 仍有边界

工作线程最多接受16 KiB文字；公共`say` API继续保留原1000字节限制。
完整最终文字的分段，不代表模型生成期间已能安全播报增量；稳定可播文字协议
仍需网关支持。长音频若超过PCM环和接收环承载能力，现阶段明确失败；没有新增
按流接收背压。worker文字上限16 KiB，公共`say`接口仍保留原1000字节限制。句间停顿、网络抖动、分段TTS请求数和实际音频质量须结合实测。
该阶段不声称解决此前TLS告警、偶发复位，也不替代真人唤醒/打断和听感验收。
