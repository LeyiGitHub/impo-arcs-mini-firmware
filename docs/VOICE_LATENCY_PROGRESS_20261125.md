# 2026-11-25：回复关联修复与链路诊断

基于 `f26bc3a`，继续使用 `codex/voice-latency`。本轮保持 `/tts`、回答音色、
原有播放缓冲策略和“小周小周”资源；交付默认仍为 batch / 1200 ms。

## 实施

- `0019` 修复完成事件的去重时机：完整文字缺少父消息时，暂不交付也不标记为
  已处理；后续同 ID 的完整事件补齐父消息后，可以通过原有 ACK 匹配并仅播一次。
  空父消息字段不再覆盖已经记住的有效关联。没有放宽串回合过滤。
- 公共快照增加订阅字节/行数、完整回复、缺少关联、文字未就绪、重复及拒绝计数。
  每轮摘要带回合编号，避免连续对话的下一轮覆盖测试数据。最后有效语音时间也
  在对应回合的短摘要中固定下来，用于声学尾部对齐。
- `voice_diagnostics` 只读查询上述计数及当前订阅是否就绪，重印前一启动的异常
  记录。启动日志早于 USB 枚举时仍可查询；`valid=0` 只表示没有可用保留记录，
  不能证明之前没有异常。异常记录仍依赖原有 noinit SRAM 保留条件。
- `0020` 对 TLS 错误记录连接年龄、成功读写的应用字节和间隔；收到致命告警时，
  仅在记录类型/长度匹配后记录两个数字：level、description。不输出 TLS 内容、
  密钥或用户消息；不改变证书校验、SNI、协议、重试和超时。
- `0021` 在发送 BIO 将非空请求的零字节返回转成连接错误，防止 mbedTLS 把尚未
  刷出的记录报告为写入成功；平台写循环也不再对零字节无限空转。由原有会话
  流程清理，不重发已提交的问题。真实加密测试复现了缺少 BIO 防护时的错误
  成功返回，加入后拒绝该写入；没有证据表明实机 TLS 告警由该边界触发。

公共快照新增字段，应用须与同一份 SDK 头文件重新编译。批量和边录边传均沿用
官方 Link；本轮没有引入新传输实现。

## 主机与构建

新增回复关联回归：旧实现对“无关联完成→补齐关联的完整重复”用例失败，新实现
通过；覆盖关联晚到、空关联不覆盖、未就绪文字及重复去除。实际采集/上传线程、
慢队列、取消、ACK 乱序、断线和语音回归通过。

异常记录生命周期在本机执行真实模块，覆盖 USB 晚查询、trap/stall 保留以及无效
记录拒绝；它不等同于实机强制异常验证。TLS 测试执行实际平台读循环及真实
mbedTLS BIO，覆盖告警、短记录、不输出非告警数据，并继续检查 SNI/证书校验。
新增真实 TLS 1.2 / AES-128-GCM 内存对端测试，在4096字节发送记录配置下传输
超过2.8 MB，刻意使用113字节部分写入、WANT 重试和交替收发，逐字节核对内容。
0.1.6、0.1.8的 mbedTLS 源码均通过；零字节退出与写超时也通过。测试证书与
确定性随机数仅用于本机测试，未进入固件。这不能排除芯片、PSRAM、网络驱动或
中继路径问题，也不能替代实机稳定性。

0.1.6 完整主机套件、默认产品及按键示例构建通过；0.1.8 Mini2 构建及镜像检查
通过。静态 SRAM 为0.1.6的152,432 B / 164 KiB、0.1.8的153,248 B / 164 KiB；
PSRAM分别5,311,760和5,313,392 B / 8 MiB。这些不是运行时峰值内存证明。
干净0018补丁前缀升级及重复 prepare 通过。

## 第一候选的实机结果

普通 batch 产品、ListenAI0.1.8，CP1,865,664 B，SHA256：
`9eea546015f4b4bdcd496538d5baeff61cb5eb751597cf64d531603659757288`。
写入前核对唯一 Recovery、保留 AP、PSRAM 声明和小周资源，读取两份当前全片一致；
写入后独立 CP 读回一致，全部非 CP 字节在本次刷写前后相同。

同一镜像内交错 batch/overlap，问题为6.321秒固定算术录音；两种模式均1200 ms，
每种4次。8/8完整问答，自动声学有效，录音丢样0：

| 指标 | batch | overlap |
| --- | ---: | ---: |
| 成功 / 尝试 | 4/4 | 4/4 |
| 说完→回答能量起点 P50 | 14.046 s | 10.651 s |
| 同一代理指标 P95 | 15.734 s | 12.821 s |
| 录音结束→全部进入本地队列 P50 | 3.518 s | 0.092 s |

P50点估计缩短3.395秒、约24.2%。样本很小，属于当前固定输入的探索；不是原始
未优化固件前后对比，也不是长期或全部问题保证。每轮完整回复计数1，缺少父消息
计数均0，因此不能据此证明关联修复就是此前120秒无回复的原因。

随后短问计划四次，实际三次：batch成功1次（尾部排队9.937秒）、overlap成功1次，
下一overlap在上传中收到 `-0x7780` 对端 TLS 致命告警。该失败只有部分音频排队，
无ACK/TTS，录音丢样0，订阅计数为0且就绪状态为false；这轮不是本地收到完整
回复后误过滤。下一计划位置因仍离线而没有发问，工具停止，没有重发失败问题。
停顿语料计划未执行。

第一候选全部11次尝试都在同一启动中，没有观测到意外重启；链路自动重连。
读/设/读确认音量恢复20%，Mac输出25%。旧重启的根因仍未确定，不能宣布已修好。
完整失败数据与成功数据均公开导出，原始音频、设备身份及日志只在私有目录保留。

`d3349ae1c697f9736ef4463932f3dbc8bbdec61604cbdfc2fb4bcb86e55233ad`。

随后中等长度输入计划8次，实际2次：batch成功，overlap上传途中失败。收到
`tls_peer_alert level=2 description=20`，即对端 `bad_record_mac`。当时连接年龄
202,555 ms，累计成功TLS应用写入1,941,582 B、读取320,312 B，距离最近写入2 ms。

该轮PCM209,920 B、排队202,752 B，丢样0，无ACK/TTS。故障点已缩小到TLS连接，
但告警本身不能判断损坏发生在本机加密、缓冲、网络还是中继路径。

代码核对显示AES/GCM走软件实现，WebSocket分块等TLS写完才复用，lwIP发送使用
COPY语义；尚未找到导致实机告警的代码缺陷。第二候选6次尝试均同一启动，没有
观测到意外重启。下一计划位置因离线未发问；失败保留，未自动重试，未执行的
6次中等长度计划不计成功。两组脱敏数据单独存于 `docs/data/voice-latency-20261125-tls-*.json`。
