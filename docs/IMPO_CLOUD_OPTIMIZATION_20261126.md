# Impo 官方更新与 ARCS 云端接入优化（2026-11-26）

结论：继续复用官方配对、TLS/Noise、Link 会话、国内路由、聊天和 TTS 是当前合适的
接入路线；现有实现仍有上传开销、长回复和可观测性方面的改进空间，不能称为最优解。
本轮实施三组可复核补丁，完成主机回归、三种交叉构建，并按后续指令刷入当前连接的
原版云宝（ListenAI AP 0.1.6）。独立读回、官方云端问答、长文本播放、显式打断和
物理唤醒基本检查通过。样本数量不足以证明稳定提速，混合压力稳定性仍待验证。

范围以当前维护的 ARCS Mini 社区 SDK 为主。官方 ESP32 的更新用于核对方向，不把
其硬件特性直接算作 ARCS 已支持。沿用已有摄像头、图片、唤醒、语音和播放回执实现，
不据本轮结果关闭小聆已有的堆损坏调查。

值得跟进的变化：

- [AAC 上传](https://github.com/impoai/impo-gadget-sdk/commit/90d1fbd5939f00eadd3f867d9cf7c15f779a7065)：带 PSRAM 的 ESP32 使用 Espressif 编码库，AAC-LC、16 kHz 单声道、24 kbit/s，经原来的文件请求上传。PCM16 的理论音频载荷是 32,000 B/s，AAC 为约 3,000 B/s；相同 Base64 包装下约为原来的 9.4%。这是载荷比，不能换算为整体响应提速比。
- [MP3 回复和独立会话身份](https://github.com/impoai/impo-gadget-sdk/commit/f1847efb6b1cc282974ac0885f61dcd839c71b14)：ESP32 的 TTS 请求改为 MP3，并为第二条聊天连接附带已注册的设备 node identity。当前 ARCS 聊天共用已注册的 Link 会话，没有该第二条连接，不能机械添加不相关的身份字段。
- [StackChan 命令调整](https://github.com/impoai/impo-gadget-sdk/commit/f5b25a979d85e6ec2193e72ac8fde2ec42b9a74a)：按其原厂固件重整硬件命令和共享命令选择；主要适用该板，不能据此删除 ARCS 已有且真实执行的能力。
- 此前主线还引入设备内嵌 description、云端准备音频、播放完成后回复等方向。ARCS 公开文件没有与 ESP32 一起完成这些迁移；本地已有精确播放回执须继续使用。

本地固定依赖仍为 `ad0e6b7` 加补丁。从它到最新主线共 9 个提交；在线 compare 显示
没有 `arcs/` 文件变化，但共享的 `esp32/main/noise_control.cpp` 有身份/描述相关变动。
因此没有整体升级依赖、移除现有产品绑定或修改配对凭据。发布版本不能只换提交号。

## 2. 各阶段评估和取舍

| 阶段 | 当前判断 | 本轮动作 | 仍需证据 |
| --- | --- | --- | --- |
| Wi-Fi、国内路由 | 已有首选网络、官方地区探测、中继/直连回退 | 继续复用 | 当前设备的重连时间和长期成功率 |
| TLS / Noise | 单会话长连接、证书/SNI 校验、心跳已具备 | 合并 WS 写入，不增大收发队列 | 慢网下实际写耗时、错误率和 RX 公平性 |
| 设备控制 | 已有 boot/playback 身份及终态回执 | 保留实际完成语义 | 云端产品/事件绑定和物理动作验收 |

| 上传 | WAV/Base64 载荷大；overlap 尚未作为稳定默认 | 裁剪有界尾部；不自动重投 | 相同录音的上传尾部和 ACK 对照 |
| ASR、Agent | 公开设备文件请求未给出实时识别契约 | 不调用猜测端点 | commit 前中间转写、排队/ASR/首文字追踪 |
| 回复文字 | 增量曾提前提交，稳定端到端收益未建立 | 保持 full 默认 | 稳定前缀契约、修订/取消/工具多消息 |
| TTS / 播放 | 长文本可能超过有限缓冲；分段预取有等待环 | 全模式限长并解除等待环；增加状态头计时 | 长回答、慢网、原音色及声学欠载 |
| 连续对话 | 播完后有 3 秒静默窗口 | 保留 | 整轮完成、迟到消息和下一轮隔离契约 |
| 多设备接力 | 完成后才发下一句会重新付出准备声音的成本 | 记录后续方案 | prepare/start 云端协议及真实逐句时间线 |

已有历史计时只能提示优先级：上传确认、首回复文字、TTS 首包各有多秒等待。
这不是本轮重测，也不能把重叠区间相加或分配给某个未经追踪的供应商。
详见[已有语音核验](VOICE_OPTIMIZATION_REVIEW_20261125.md)。

连接还有一个需单独处理的边界：`plat_tls_connect_named()` 在设置 non-blocking 前
调用 `mbedtls_net_connect()`；本地两个 ListenAI 版本的该函数均先同步解析域名，
再调用 connect，没有接收本层 `timeout_ms`。因此本层握手/读写期限不能当作
DNS + TCP + TLS 的统一连接上限。这是源码发现，未证明它导致过哪一次现场停顿。
后续应优先补分阶段计时和有界 TCP 建连，再验证解析超时、多地址回退、SAL socket
关闭及两个 SDK 的行为；本轮没有用一个未经平台验证的连接器替换现有路径。

## 3. 已实施的代码

### 3.1 合并 WebSocket 写入

`patches/0030-coalesce-websocket-writes.patch` 修改共享官方写函数，ARCS 通过兼容层
选择 4096 B 暂存。典型 2048 B payload 连同帧头只需一次 TLS 写，原路径是一次
帧头加四次 512 B payload。暂存首次使用时分配，ARCS 放入 PSRAM，跨重连复用；
不增加固定 SRAM 大数组，不在每帧 malloc/free，不改变 Noise 数据或调用者缓冲。

首块包含 WS 帧头；后续块仍用原 payload 偏移计算掩码。所有块共用一条帧的外层
15 秒期限，partial write/WANT 只续写尚未交付的字节，零进展、错误、停止立即退出。
底层 TLS 写本身有独立期限，外层检查发生于底层调用之间，不能声称可抢占该调用。
同时修正大帧长度字段在 32 位目标上的移位类型。

接收容量、small-session 档、4096 B 请求 body 预算、官方心跳、国内路由、证书验证
和凭据刷新均不改。减少写调用是主机可验证的结果，线上时延和 TLS 记录数另测。

### 3.2 批量录音尾部裁剪

`patches/0031-batch-voice-tail-margin.patch` 配合公共 API：

```c
impo_arcs_mini_configure_voice_tail(300); /* 空闲、batch 时接受；0 恢复关闭 */
```

默认关闭。允许 200～1000 ms 保留量，只在正常静音端点结束时去掉超过保留量的
末尾低于 VAD 阈值的音频。保留开头、中间停顿和尾部余量，重新写 WAV 长度；
超长录音、无语音、取消和失败不走正常裁剪。overlap 模式明确拒绝开启；已开启时
也拒绝切换 overlap，避免裁剪已经发布或上传的前缀。

本地 shell 使用 `voice_tail 300` / `voice_tail 0`；需先结束连续会话。
该配置不写 KV，重启关闭。`voice_diagnostics` 和对应回合日志记录
`tail_keep_ms / captured_pcm_bytes / trimmed_pcm_bytes`，不会记录原音频。
裁剪只减少提交字节，**端点仍等待 1200 ms**。VAD 阈值不能证明轻声末字已结束，
所以未经实机收音/听感验收不能默认开启。模拟输入裁掉 900 ms，准确减少
28,800 B PCM（38,400 B Base64），仅代表该测试输入的字节结果。

### 3.3 有界 TTS 和长回复等待环

`patches/0032-bound-tts-segments.patch` 将单次 `/tts` 请求限制为最多 120 个 Unicode
码点，适用于 full、sentence 和 incremental 的最终剩余后缀。优先保留句子/空白边界，
无标点长串也按完整 UTF-8 码点切分。逐段拼接严格还原输入，不添加标点或重播前缀。
短于上限且未启用 sentence 的文字仍为单笔 TTS；长回答可能增加 TTS 次数和段间等待。

完整缓冲模式原本需要 25 秒预填，分段生产者却在 30 秒环的可用空间少于 24 秒时
停止预取，导致环内有 6～25 秒音频时互相等待。现在在该预取门槛释放同一代次的
初始缓冲，让已有音频播放并腾出空间；不把输入标记为结束，不伪造 completed，
不能让旧代次释放新播放。adaptive 模式的预填与欠载处理仍沿用原实现。

文本上限不保证音频时长，64 KiB ingress 和 30 秒 PCM 环仍有限；极慢语速或异常
过量返回仍会明确失败。没有把有限缓冲描述成无限背压。新增
`first_submit_ms / first_status_ms` 区分本地请求提交和响应头回调，基准工具兼容旧
快照并导出相对耗时。这些时间不能冒充实际 socket 发完、服务端 ASR 或供应商耗时。

### 4.1 原版云宝刷写与基本回归

重新核验 Recovery 唯一编号、当前 CP、ListenAI AP 0.1.6 和“你好云宝”原唤醒资源。
两份 16 MiB 全片备份一致，Boot/AP/资源与已有核验基线一致；仅向 `0x600000`
发送一次 yunbao / 0.1.6 候选写入。独立 CP 读回与上述镜像逐字节相同，完整读回
确认所有非 CP 字节不变。配对和音量 60 保留，重启后 Link 在线且聊天订阅就绪。
本轮只刷这一台；另外两份候选只有构建和镜像检查结果。

使用同一固定外放问题“请只回答一个数字，二加三等于几？”，保持同一启动、音量、
batch / 1200 ms / full / complete 播放策略，先关闭裁剪，再开启 300 ms，各测一次。
两次均只有一笔聊天请求、一笔 TTS、录音丢包 0，回复解码和设备输出完成。

| 捕获 PCM | 172,800 B | 172,160 B |
| 裁剪 PCM | 0 B | 28,800 B |
| 提交 WAV | 172,844 B | 143,404 B |

## 5. 后续实施与上线门槛

1. **补齐同机和其他设备回归。** 本轮原版云宝已完成上述基本检查；仍保留可恢复
   镜像。其他设备须重新核验 AP、资源和 CP 身份后只写对应 CP。多条回复、长中文、
   人工听测、断网恢复和混合压力仍需分别验证。小聆既有堆损坏未修复，不能批量推广。
   同时为 DNS/TCP 建连补上独立验收用例；收集连接阶段耗时后完成上述期限缺口。
2. **独立测试裁剪。** 同镜像、batch/1200/full、同音量及播放策略，交错比较
   `voice_tail 0` 和 `voice_tail 300`。固定语料覆盖句内停顿、轻声尾字、数字及噪声；
   保留所有失败，检查一次消息提交、识别完整性、声学首声和截尾，收益不预填。
3. **再接入压缩。** MP3 回复优先评估：ARCS 已有 Helix 整文件解码用于 play_url，
   但 `/tts` 的分块解析、截断、尾部、取消和持续解码仍需实现与真机验证，不能只改
   Accept。AAC 编码不能使用 ESP 专属二进制；需选定 ARCS 编码器并核验许可、
   CPU/内存和中文转写。两者都以功能开关独立对照，不与端点修改混为一组。
4. **云端协作解除更大的等待。** 沿用[流式 ASR 接入要求](CLOUD_STREAMING_INPUT_AUDIT_20261125.md)：
   明确能力发现、音频未封口时的中间识别、turn 幂等、取消和最终提交。另补 Agent
   排队/首文字、TTS 请求/首音频追踪。设备代码无法独立消除这些未暴露阶段。
5. **轮间和多机单独处理。** 有完整 run 结束和迟到消息路由后再评估缩短 3 秒窗口；
   接力需要显式 prepare/start 音频能力，在上一句播放时准备下一句，completed 只
   触发已准备内容。现在的 say 会出声，不能拿它当静默预加载或直接并发播放。

候选默认仍是 batch / 1200 ms / full，tail 关闭。播放策略继续由产品配置决定。
未承诺确定的端到端节省秒数；稳定性、输入完整性和实际声音结果均须单独记录。
