# 2026-11-25 语音全链路延迟分析

用户感到仍然慢，与现有测量一致。最终播放优化镜像在网络恢复后的两轮完整问答中，
从固定问题最后一个有效语音帧到麦克风检测到回答首声，分别为 **13.710 秒、17.296 秒**。
此前“缩短40.2%”对应固定文字的 **TTS命令到首声** 对照，不是完整问答提速40.2%。

本次重新分析已有设备日志、Mac麦克风录音、逐轮计时、固定字段导出和当前源码。
没有云端日志，没有重新发问、修改设备配置、刷写或重启。设计稿中的目标不当作已实现能力。
这里的两轮是小样本恢复检查，没有全链路对照组，不报告有代表性的P95或失败率。

分析对象为分支 `codex/voice-latency`、提交 `6aed7a3` 对应的最终Mini2镜像：
ListenAI 0.1.8，CP SHA256
`90d0638523d57355c7530e3cb9893c3e19593f49425a20dc2f6d875d0e8d876c`。
上传为batch，端点1200 ms；播放为adaptive/1200/full，官方`/tts`、原音色、小周资源。
这是既有实测镜像的分析，不是本轮重新核验USB设备当前运行状态。

后续已补齐实际增量观察点并实现可选队列播报，详见
[增量改造与独立验收记录](INCREMENTAL_REPLY_20261125.md)。下文保留本次分析时
全文播报镜像的边界；其计时不与后续候选混合。

## 正常问答慢在哪里

下表除最后一行外均为同一设备单调时钟的阶段差，单位为秒。前九项相加严格等于
“最后有效语音→驱动首次接受回答PCM”，并非把跨机器时间戳直接相减。

| 阶段 | 第1轮 | 第2轮 | 能确认的含义 |
| --- | ---: | ---: | --- |
| 最后有效语音→采集结束 | 1.195 | 1.219 | 1200 ms静音端点 |
| 采集结束→上传任务开始 | 0.054 | 0.061 | 本地任务启动等待 |
| 上传任务开始→请求体全部进入本地队列 | 2.075 | 4.671 | 编码、分块和发送队列反压的合计 |
| 全部本地入队→匹配ACK | 1.194 | 1.518 | 剩余发送、往返、远端接收处理等；无法继续拆分 |
| ACK→匹配的完整最终文字 | 5.095 | 4.707 | 完整回复的等待；不能直接等同于模型推理耗时 |
| 完整文字→提交TTS工作线程 | 0.022 | 0.086 | 本地语音状态机调度 |
| TTS提交→首个音频响应体字节 | 3.117 | 4.220 | 包含本地请求排队、传输、远端合成与转发的总等待 |
| 首个响应体字节→首个PCM | 0.001 | 0.005 | WAV解析并产出第一批样本；不是整段音频的总解码耗时 |
| 首个PCM→驱动首次接受 | 0.436 | 0.401 | 起播储备与音频输出调度 |
| **设备最后有效语音→驱动接受合计** | **13.189** | **16.888** | 尚未等同于实际声学首声 |
| **原始问题尾部→检测到回答能量** | **13.710** | **17.296** | 独立录音测得的自动声学代理 |

两轮中位数：采集结束至ACK为4.787秒，ACK至完整文字4.901秒，TTS提交至首包
3.669秒。三者合计13.356秒，占设备最后有效语音至驱动接受区间的约88.8%。
这些区间含有本地和传输等待，**不能把88.8%称作云端耗时占比**。

设备区间与声学区间相差0.521/0.408秒。VAD最后语音与固定录音尾部的对齐误差为
-6/+26 ms，首声自动检测均有效。剩余差值可能包含音频前导静音、输出链路、能量
阈值及观察误差；没有DMA完成与校准声学测量，不能把它全归为扬声器硬件延迟。
两轮丢样均0，均仅1次聊天请求、1次完整匹配回复、1次TTS，未观察到回复被错误过滤。

## 上传仍然占据用户说完后的关键路径

当前batch模式会等整段录音结束，再把完整WAV交给上传任务。两轮分别采集
167,680/167,040字节PCM，采集结束时的待传WAV为167,724/167,084字节，等于整段WAV。
因此“采集和上传有独立任务”不代表当前产品已启用边录边传。

16 kHz、单声道16 bit PCM每秒32,000字节，当前约5.2秒采集产生约167 kB原始音频；
Base64后约223 kB，尚未算JSON、Noise、WebSocket和TLS封装。尾部1200 ms静音本身
约38,400字节PCM、51,200字节Base64。它既延后端点，也增加batch上传量。

第2轮记录到同一次反压的两个观察点：

- TLS写512字节用了 **1953 ms**。
- 外层8192字节请求体入队调用用了 **1984 ms**。

它们时间重叠，不能相加成3.937秒。第2轮采集结束至入队比第1轮多2.603秒，
这次阻塞能够解释其中很大一部分。它证明等待发生在实际发送/队列链路，不能据此
认定是Base64计算慢，也不能分辨Wi-Fi重传、TCP窗口、对端读取、TLS调用或调度各占多少。
日志只对单次较慢调用输出，不出现慢写日志不代表上传没有累计等待。

当前ARCS兼容配置选用官方small-session档：请求队列长度6、累计body预算4096字节，
外层再按2048字节分块，发送受底层消费速度限制。这解释了为何“入队”也会受网络
反压影响。该档同时关系到入站帧兼容，不能直接切换整个内存档或盲目加大队列来宣称解决。
`upload_queued`只代表本地接受全部body，不是最后一个字节已上网或已到服务器。

已有overlap试验曾缩短录音后的上传尾部，但还出现TLS告警及未知复位，因此没有提升为默认。
这些实验收益与失败见[逐候选记录](VOICE_LATENCY_PROGRESS_20261125.md)，不能只取成功数字。

## 完整文字和TTS首包仍然串行

当前先等待可关联、文字就绪的完整`delta.message_done`或`message.assistant`，再提交TTS。
所以用户说完后要先等待完整回答文字，再等待语音首包。当前没有在模型生成期间
播报已稳定句子的能力；可选“按句TTS”只切分**已经收到的完整最终文字**，不能消除前面的完整文字等待。

ACK仅表明请求返回HTTP 200且确认消息可解析，不证明识别已完成或模型已开始生成。
ACK至最终文字的4.7～5.1秒可能跨越识别、排队、模型、工具和事件转发；现有日志
没有首个文字增量时刻，不能判断其中多少是“模型第一个字慢”、多少是“等整篇生成完”。
两轮完整消息计数均1，缺少关联、文字未就绪和重复/拒绝计数均0，没有观察到本地过滤造成等待。

同理，TTS提交到首个音频字节的3.1～4.2秒不是纯合成时间。阶段6现在表示提交工作线程，
并非HTTP请求已实际写出；已有日志没有请求首尾实际发送时刻及远端处理子阶段。
两轮都复用同一个已连接会话，没有逐轮重连证据，不能把这些秒数归因于每次DNS/TLS握手。

## 播放优化确有收益，但剩余空间已经小很多

最终同镜像、相同固定文字、交错顺序的20轮对照，与上面的完整问答是不同实验：

| 指标 | 完整缓存 | adaptive/1200/full |
| --- | ---: | ---: |
| 完整播放 | 10/10 | 10/10 |
| 声学有效样本 | 7 | 8 |
| TTS命令→检测首声 P50 | 7.959 s | 4.756 s |
| TTS提交→首个响应体 中位数（各10次） | 3.606 s | 3.872 s |
| 首响应体→首PCM 中位数（各10次） | 0.0035 s | 0.0030 s |
| 首PCM→驱动接受 中位数（各10次） | 3.5375 s | 0.4870 s |

收益集中在本地等待缓存：该指标少了约3.05秒，远端首包等待没有因此缩短。
各项中位数不是同一轮数据，不要求分项中位数相加等于总中位数。声学拒绝样本仍保留，
没有补值。40.2%仅适用于这个固定文字播放实验，不是当前完整问答的前后对照。

当前两轮完整问答的首PCM至驱动只剩0.40～0.44秒，首包至首PCM仅1～5 ms。
继续微调解码或把起播缓冲压得更小，不能解决前面十余秒等待。
1200 ms是“已解码音频内容长度”的初始储备，不是强制等待1200 ms墙钟时间；
当前实际储备只花约0.4秒。直接去掉它也不能承诺省1.2秒，且已有800 ms候选出现欠载。
原始短回答的缓存等待也可能已经很短，不能把固定长文字的3秒收益套用到所有问题。

## 异常时为什么会等到几十秒甚至超时

同一最终镜像还有一轮不同问题的失败，必须与恢复后成功的两轮分开看：

- 端点1.186秒；采集结束至本地入队2.413秒；本地入队至ACK4.401秒。
- **ACK至完整文字25.331秒**，明显长于恢复后两轮。
- 收到完整文字后发TTS，但没有音频；45秒无进展后失败，沿用原语音状态机的一次
  “尚未起播”TTS重试。重试又等待约42.5秒，仍未出声，被测试工具120秒等待上限主动取消。
  原聊天问题没有重新提交，第二个计划问题没有发出。
- 后续连接记录为接收静默150,076 ms后以`gateway silent`结束会话。多次查询打印的是
  同一条历史结束记录，不是发生了多次相同断线。

这不是“本地解码算了45秒”，而是没有拿到可解码数据。连接在长时间静默时仍可能
保留online状态，原有TTS重试于是继续等待，放大了用户可见的无声期。缺少请求状态、
包级和云端证据，不能确定停在本地传输、网关转发还是TTS上游；也不能宣称已定位云端故障。

另一次受控重启后的日志明确显示：Wi-Fi已关联、DHCP已有IP、配对仍在，但多个NTP域名
DNS解析失败，时钟未同步。Link的启动流程要求先校时以进行证书校验，因此保持idle；
约236秒后才自行校时并上线。这证明“连上Wi-Fi”不等于请求链路可用。它是重启后的
独立上线阻塞，不能反推成前一轮TTS失败的根因，也不能算进每轮正常问答耗时。

## 连续对话还有一段独立的迟钝

回答播完后，`await_replies()`还固定等约3000 ms安静期，确认没有后续回复才结束回合；
连续收音前再等待300 ms输出尾部，并执行提示音和150 ms收音准备。
两轮日志的播放结束至回合摘要分别为3.100/3.092秒，下一次收音提示音约3.48秒后出现。
这会让“说一句、答一句、再接一句”显得迟钝；它不在上面13.7/17.3秒的首声指标里，不能重复相加。
开启收音后的500 ms噪声校准发生在输入阶段，也不能再加到用户说完后的等待上。

## 没有云端日志时的下一步顺序

1. **补齐本地关键边界，优先解释上传和无响应。** 给每个请求记录排队、实际首/末发送、
   状态头、首/末响应体、结束/取消原因，以及会话最近一次收发间隔。增加有界的慢写
   分布、队列水位和可取得的TCP/Wi-Fi计数；不打印内容、凭据或协议明文。
   同时给订阅事件记录类型和到达时间，拆出首个增量至最终文字，避免继续把整个区间叫作模型耗时。
2. **处理上传的实际阻塞及无进展恢复。** 在同一镜像、相同输入、交错顺序下定位慢写，
   验证队列预算、发送节奏与会话健康；只有TLS稳定性门槛通过，才考虑将已有overlap作为默认。
   无数据时要有请求级的反馈和有界退出，不能只靠150秒连接静默阈值及45秒后的同会话重试。
   退出更快属于失败体验改善，不应包装成成功问答提速，也不重发状态未知的聊天问题。
3. **单独改善下一轮收音的3秒固定等待。** 优先明确多回复结束信号、迟到消息处理和
   播放尾部约束，再验证提前收音与打断；这项可以直接改善轮次衔接，但要保留正确回合关联。
4. **再争取文字生成与TTS重叠。** 本地先测首个文字增量何时到达；真正提前播报仍需要
   可关联、稳定、不回滚的文字契约。当前完整文字分句选项不能替代它。
5. **端点和播放缓冲作为次级优化。** 1200→800 ms端点在相同判定下理论少400 ms，
   同时减少静音上传量，但需句内停顿验收；不能期待它把15秒问答降到几秒。

本轮确定的是慢的区间、串行依赖、一次实际发送阻塞和异常等待机制。识别、模型、工具、
TTS供应商及网关各自耗时仍未知。优先级应从继续压播放缓冲，转向上传/连接健康、
完整文字至首包的串行路径，以及连续对话的固定3秒等待。
